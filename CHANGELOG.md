### Added
- `config/settings.json` carries a third `SessionStart` hook that `direnv allow`s the `.envrc` Claude Code's built-in worktree copied (STARK-5090). `claude -w` honors `.worktreeinclude` and copies the file, but the helper it replaces (`stark-workspace/scripts/copy-worktree-environment.sh::allow_direnv`) also trusted it, and direnv keys its allow-list by path **and** content hash — the main checkout's grant covers neither an identical copy at another path nor a later edit — so every fresh worktree in a gcp-scoped repo opened with `direnv: error .envrc is blocked` and no per-repo scope. `WorktreeCreate` was wrong (a *replacement* hook: it must create the worktree itself and echo the path, taking creation away from the built-in) and `Setup` never fires on a `-w` launch even with matcher `*`; `SessionStart` does, with cwd already inside the worktree. The guard is narrow on three axes: it derives the **worktree root** from the session cwd rather than allowing cwd, so a session started in a subdirectory still trusts the root `.envrc` (`direnv allow .` silently left it blocked); it requires that root to be a real linked git worktree (`.git` present as a file), so a directory merely *named* `.claude/worktrees/<x>` in a checked-out tree is never auto-trusted; and `matcher: startup` keeps it off `resume`/`clear`/`compact`, so an `.envrc` edited mid-session is re-blocked until a human runs `direnv allow`. It deliberately never auto-trusts an `.envrc` outside `.claude/worktrees/`. **Delivery:** this needed `stark-workspace` STARK-5223 first. `setup.sh` merged the template *under* the live `~/.claude/settings.json` with a shallow `jq '.[0] + .[1]'`, so a live file that already had a top-level `hooks` key kept its own and never received any template hook — this one would have merged green and shipped nothing (the template's own `.remember/logs` hook had never reached an existing machine for exactly that reason). setup.sh now unions hook entries per event, keyed on (matcher, command list), so an existing machine receives it on the next run. The `deniedMcpServers` note in STARK-5030 still describes the shallow behaviour, which is unchanged for every key except `hooks`.
- `gru sweep [--run ID] [--apply]` releases reservations that can never progress, on proof rather than age (STARK-5037). The store had no prune path: a launch that never attached, followed by `stop`, held its ticket, worktree, and files forever, so a corrected run failed with `file ownership conflicts` even after both tickets closed outside the store, and the operator cleared the SQLite rows by hand. A held task is released only when Alfred reports its ticket `done` or `Closed` AND no live Hermod peer is bound to it: a bound worker must be observed terminal under `reconcile`'s own rules (`unknown` stays held), and with none bound, discovery must find no live or uncertain peer inside any worktree the task owns, which may be the launch that never attached; the store checks peers against the task's actual `tree:` owner rows, the rows a release deletes, so the reserved worktree, one an earlier takeover retired, and a declared one `attach` kept when adopting Hermod's actual worktree are all covered. Occupancy reads every provider and ACP peer, so both that unscoped view and the task's own namespace must report complete, and a same-provider peer with no resolvable working directory counts as an occupant, as does a saved session in `hermod sessions --all` whose pid probes alive (`alive: true`) even when the peer view omits it, since takeover's absence checks already read both sources. An integration grant stays held, because a worker closes its ticket at merge and `verify` still settles it once the PR merges (a grant whose PR never merged stays held too); so do an uncertain reconnect and a `reserved` launch in a still-`running` engagement, which Hermod cannot show before it registers. Alfred refuses work verbs outside a git checkout and binds ClickUp or Jira from the checkout's org, so a machine-wide sweep run from `$HOME` fails, and a Jira-bound task repository reads its ClickUp `STARK-n` handle as missing; sweep tries the swept tasks' repositories, every other repository the store records (so `--run` on a Jira-bound engagement still has a ClickUp checkout), then the caller's directory, until one yields validated evidence for a ticket, reads the rest there, and reports every context's error when none does. The default dry run opens the store read-only (no directory, permission, journal-mode, or schema change), and neither mode creates a missing store. `--apply` gathers all Alfred and Hermod evidence first (either failing exits 2 with nothing released), then writes each engagement in one store transaction fenced on the exact revision the evidence was gathered at and one-minute evidence freshness. It needs no leader identity: each release records a `swept` event and `task.swept` stating it was a proof-based sweep, not a leader action, with the invoking session, leader of record, proof, and released resources. A released task enters phase `swept` and drops its worker and observation (the record keeps them), so it holds no owner rows, files, or capacity, is not verifiable, and is no longer listed as waiting in `status`. A run whose tasks are all verified or swept enters terminal mode `swept`, which `resume` and `stop` refuse; `verify` applies the same rule, so verifying the last task after a partial sweep settles the run too, where a sweep with no candidate left never would. `--apply` is refused on every other verb, and sweep refuses the flags it would ignore. Worktree adoption no longer counts a swept task's leftover declaration of the path it released, matching `reserve`.

### Fixed
- **`gru integrate --base` is checked against the repository, not just its hex shape (STARK-5051).** The store accepted any `/^[0-9a-f]{40,64}$/`, so a foreign-repository SHA, a typo, and an hour-stale tip all passed; `verifyCompletion` then only requires that base in the merged head's ancestry, so a diff built without another task's merged changes squash-merges cleanly whenever git sees no textual conflict. STARK-5049 let tasks with overlapping files dispatch in parallel, which left that window as the remaining hazard, closed until now only by prose telling the leader to grant at a freshly fetched tip. `integrate` now gathers git evidence before the store transaction (`observeBase` in `gru_runtime_lib.ts`): it confirms the checkout's origin is the task's repository, fetches the base branch from origin into an invocation-owned `refs/gru/integration/<uuid>` (no `FETCH_HEAD` write, no checkout movement, ref removed afterwards), resolves the supplied SHA to a commit that repository holds, reads the branch tip, and tests each of this engagement's verified merges for ancestry. The pure `baseRefusal` in `gru_lib.ts` then judges: complete and fresh evidence, matching repository, evidence covering the supplied SHA, the SHA equal to the tip — the refusal names the current tip — and containment of every merge this engagement verified onto the same base branch, which is the offline floor that survives a wrong or raced fetch. That floor is scoped by branch (`task.baseEvidence.ref`, newly retained for audit) so a repository that also merges onto a release branch does not have a perfectly current `main` tip refused for lacking commits that were never on it. Fail-closed throughout: an unreachable origin, a branch origin does not have, a malformed branch name, and an origin reporting no default branch each refuse and name which, instead of falling back to a local ref that reads exactly like a current one. The base branch is origin's default unless `--base-ref BRANCH` names another, and that name is asked of origin (`git ls-remote --symref origin HEAD`) rather than read from the local `refs/remotes/origin/HEAD`: git writes that pointer at clone and then only on an explicit `git remote set-head`, so a checkout made before a default-branch rename still names the old branch, which usually still exists and is frozen — every supplied base then passes as "the current tip" and the whole guard is off while the refusal text, the docs, and the recorded `baseEvidence.ref` all report it on. Asking origin costs a second round trip (`ls-remote` and `fetch` are separate connections, and `--base-ref` skips it), which is worth paying to keep the one local input that could lie out of the decision. That flag and `--base` are refused on every other verb rather than silently ignored, since a parsed-and-dropped `--base-ref` would read as a grant checked against the named branch. The observation runs before the transaction, so a failed fetch never takes the repository merge lock — and the CLI refuses a task that is not in `review` (or an engagement that is not running and reconciled) *before* the fetch, so a grant the store was always going to refuse never spends a network round trip or writes objects into the leader's checkout. `verify` closes the other end: the grant's branch (`baseEvidence.ref`) must be the branch the PR actually merged into, because `--base-ref` is operator-supplied and a grant taken at a quiet branch's tip — current by definition, with an empty floor — would otherwise discharge a merge into `main` that skipped every other task's changes. Three edges the bifrost#264 publish review caught, fixed before publication under STARK-5088: an unknown object from `merge-base --is-ancestor` (exit 128) is only an answer in a complete clone, so a shallow one now refuses by name (`run git fetch --unshallow`) instead of reporting every older merge missing and telling the leader to fetch again, which cannot work; both network round trips are bounded by half the observation freshness window, so a slow fetch fails as a fetch rather than returning evidence the store then calls stale; and the `verify` branch-mismatch refusal names the repair, including the fact that a grant cannot be retaken once the task is `integrating`. `/gru` (both runtimes), `operations.md`, `CLAUDE.md`, and `AGENTS.md` now state the enforced rule rather than the leader obligation it replaces; each new guard is pinned by a test that fails when the guard is deleted — the flag-scope refusal, the shallow-clone refusal, and `verifiedMerges` excluding the subject task by `spec.id` rather than by object identity, which two separate parses of one run would otherwise put in its own containment floor. Five more from the `/code-review` pass on the same PR, all of them refusals that could not be acted on: the stale-tip refusal now offers `--base-ref` as well as the tip, because a task whose PR targets another branch reaches that exact refusal and "grant at the tip" alone walks it into the unrecoverable mismatch `verify` then refuses; the verified-merge floor names a revert or force-push off the branch, the one way that floor can never be satisfied by fetching; the shallow-clone probe moved to one per-repository check before any comparison, because the graft also produces exit 1 — a false "not contained" the per-merge 128 reading let through into the same cannot-work loop; the whole observation, not just its two network calls, now refuses when it outlives the store's freshness window, so slow local ancestry work fails as the slow observation it was instead of returning evidence the store rejects with "fetch the base branch again"; and the symref round trip explains its own timeout like the fetch beside it. The dispatch packet also names the branch a pending grant was checked against, since a worker resuming an existing PR is the only one who can still retarget it.
- **Deterministic Minion re-brief intake (STARK-5046).** `gru rebrief-check` reads the Hermod ledger and returns the accepted packet without opening the leader's database. The packet and Claude/Codex Minion and Gru skills use that command. `resume` records portable transfer evidence for workers whose process discovery is sandboxed; locally visible live leaders still block transfer. Re-briefs are notes and their acknowledgements are fresh progress messages, avoiding the 30-minute request reply deadline. Resume guidance now escalates an unconfirmable transfer and the Codex variant names `CODEX_THREAD_ID` for attribution. Ordering is authority-aware as well as chronological: `createdAt` is send time, so a revived leader resending a pre-transfer packet would win on it alone; the check also refuses an older `epoch`, and reports which replay check ran (`newer`, `reread`, or `unchecked` with no current message). The chain in a packet is the most recent 16 transfers, because Hermod refuses a body over 32 KiB. Packet free text is indented at its line breaks, so a multi-line objective or done-when cannot forge a second header and refuse every re-brief for that task. Message ids match case-insensitively, as Hermod's own do.
- **Gru's integration-grant rule says the right thing (STARK-5049).** The bifrost#259 publish review caught an over-correction I shipped one PR earlier. Pinning the grant to "the base the previous merge produced (its verified `merge` commit)" is wrong twice: a base branch also takes direct publisher pushes, so the previous merge commit can sit behind the tip; and `merge:<repo>` locks are global, so that merge can belong to an engagement whose commits this leader never recorded. It also had no case for the first grant in a repository, where no previous merge exists. The rule is now **the base branch tip the leader fetches and reads immediately before `integrate`** — not "under the merge lock", which names an ordering no command offers: `integrate` takes `merge:<repo>` in the same transaction that records the base, and refuses a second call once the phase is `integrating`, so a fresh fetch immediately before the call is the whole rule and the lock refusal (now naming its holder) is what tells a leader to wait, fetch, and read again. Stated in `/gru` (both runtimes), `operations.md` (including §Verification and integration, which still prescribed the pre-merge "freshly observed base commit" the new paragraph called unsound), `research.md` (the one published contract the previous pass missed, and the file `/gru` names for protocol authors), `CLAUDE.md`, `AGENTS.md` (both of which the previous pass gave the retracted wording), and `verifyBlocker`'s three runtime hints, which a leader reads exactly when it integrates — now one shared constant, so they cannot drift apart again. **Worker side:** the packet and `/minion` (both runtimes) now name the rebase target, the base branch's current tip rather than the granted SHA, require reposting the review, and require sending Gru the new head SHA and review id before merging — `gru verify --review N` takes the id the leader last heard, so a repost the worker never reports is evidence Gru cannot reach. The packet also carries the exclusive-resource rule, since it is the only brief every worker gets. Without that, a routine post-merge rebase changes the head, `verify` refuses a review whose commit is not the merged head, and nothing can repair that evidence after the merge, leaving the task holding the global merge lock. `/minion` also asks for "any exclusive resource not listed in your packet" instead of "one another task holds", which a worker cannot observe. **Contention:** `resource already owned` now names the holding run and task, so waiting on a live peer and a dead engagement's hold no longer read alike.
- **Gru's contracts follow STARK-5049 through, from the bifrost#258 publish review.** Leftovers from the overlap change, in every contract that carries it. `/minion` (both variants) told a worker to "raise missing scope or conflicting ownership before touching shared files", which would make one of two Minions with overlapping files report `blocked` instead of implementing, re-creating the stall one layer up in the prompt; it now says overlapping files are expected, to implement and reconcile at the rebase, and to report only scope outside the declared files or an exclusive resource another task holds ("raise scope outside your declared files" was itself ambiguous enough to read as an instruction to expand scope). `packet()` carries the same line, because it tells the worker to run `/minion` only "if available" and is therefore the one brief every worker actually gets. `operations.md` restores "and engagements" to the takeover retention sentence, because `exclusive:` owner rows are global (`ownedElsewhere` queries without a run filter) and the narrowed wording pushed an operator toward the hand-edit the same document forbids. It also states the leader obligation that makes rebase reconciliation sound: grant `integrate` at the base the previous merge produced — its verified `merge` commit — never one observed before it, since the store validates the SHA's shape alone (40 to 64 hex characters) and `verify` only requires that base in the merged head's ancestry. `/gru` (both variants), `CLAUDE.md`, and `AGENTS.md` stated the overlap claim without that precondition, so they carry it now too. The `swept` audit record and the `sweep` verdict no longer carry `files` beside the owner rows they released, which advertised a freeing that can no longer happen; both are now pinned by a test.
- **Gru no longer blocks dispatch on overlapping files (STARK-5049).** `readyReason` refused a task whose declared `files` overlapped another task in the same repository, within an engagement and across engagements. That added no correctness: every worker edits its own worktree, and overlap reconciles where git resolves it, at the rebase before merge (a 3-way merge). It only cost dispatch, and a dead engagement's hold could strand it for good. The repository merge lock already makes merges go one at a time. The leader grants integration at the current base SHA, and `verify` then requires that base in the PR head's ancestry, a posted review on that head, and the declared checks rerun on the merged base. The store cannot see ancestry itself, so a grant at a stale base does not force the rebase. On 2026-09-17, STARK-5046 was refused over `tools/gru.ts` held by the dead `stark-4968-followups` engagement: its leader and workers were absent from complete Hermod discovery, STARK-4985 was Closed and its work merged, and neither `sweep` nor `takeover` could release a worker observed `unknown`. Declared `files` still scope each worker's brief. Exclusive resources, ticket and worktree ownership, and the `merge:<repo>` / `merge-resource:` locks are unchanged. The pure `readyReason` also dropped its in-memory exclusive-resource loop and the `pending`-after-takeover predicate behind it: both duplicated the store's `exclusive:` owner rows, which every stopped or taken-over task keeps, so a same-engagement conflict now reads `resource already owned: exclusive:<name>`, as a cross-engagement one already did. The store no longer loads every other engagement to compute readiness; adoption's declared-worktree check still does.

- **A Gru leader that declared the wrong worktree layout orphaned its reservation (STARK-5039).** On 2026-09-17 a leader declared `<repo>/.worktrees/STARK-5030`, and `hermod ticket STARK-5030 --agent claude` (v0.17.4) placed the worker in `<repo>/.claude/worktrees/STARK-5030`. `attach` refused with `worker worktree mismatch`, correctly, but that left the live worker unbound: nothing could attach, interrupt, or recover it, and the reservation held its ownership forever. `attach` now adopts the observed worktree instead of refusing. - **Gru re-brief is screened by the worker against Hermod's ledger (STARK-5039).** Raised independently by the review of bifrost#256 and by the STARK-5037 session's review of its own publish. **(1)** The packet and `/minion` said a later packet "from this leader or one that took over the engagement" supersedes the brief, but a worker could not verify a takeover claim, so any peer could send a packet naming itself leader with a new token and worktree. A superseding packet is now judged from Hermod's ledger record (`hermod msg status <id> --json`), never the delivered text, whose envelope header is only data: the record must be addressed to the worker and attributed to the leader session the packet names, the worker acts on its `body`, and that leader must also be either the current leader or a new one while complete discovery (`incomplete: false`) has no live record of the current leader session, the discovery evidence `gru resume` requires. Anything else is task data. The leader confirms its own re-brief shows it as `sender`, since Hermod attributes a Claude sender only from its cmux surface. **(2)** A Minion whose packet names another checkout was told to report an intake blocker, but `receive` can never import that report: no worker is bound before `attach`, and adoption replaces the token. It now sends a plain Hermod note naming its actual checkout and starts no work until the later packet arrives; the packet itself carries that rule for a worker without `/minion`, and `receive` names such a note as not a JSON report instead of surfacing a raw parse error. `/gru` (both variants) and `operations.md` tell the leader to send re-briefs through Hermod from its own session. **(3)** The review of bifrost#257 found that this still overclaimed, and it closed three gaps. **What the screen is not:** Hermod derives sender identity from the sending session's own environment, so these checks screen mistakes and relayed text, not a hostile local process. The packet, `/minion`, and `operations.md` now say so, and say that Gru's store token fence stays the authority: it refuses reports under a token it did not issue, so a wrongly accepted packet cannot advance Gru's records, though it can still misdirect the worker. **Gaps closed:** the record must also be not `failed` or `cancelled`, and newer (`createdAt`) than the packet the worker follows when that packet has a record, which stops a cancelled or replayed re-brief. `expired` is deliberately not screened: `hermod msg status` persists it on a request past its 30-minute reply deadline, which a delivered re-brief outlives. Leader absence is judged on a peer's `liveness`, as `gru resume` does, never its `state` (a live leader reads `busy`). After session resumption a worker rereads the latest accepted packet, not the replaced launch brief. `destination.sessionId`/`threadId` is named against `CLAUDE_CODE_SESSION_ID` (or legacy `CLAUDE_SESSION_ID`)/`CODEX_THREAD_ID`. A worker whose discovery stays incomplete sends the named leader a plain note rather than stalling silently, and the leader escalates. A leader whose re-brief shows no sender sends it again with a fresh `hermod msg send` from its own cmux surface (`hermod msg resend` copies the missing sender) or escalates. `receive` checks the message is addressed to the leader before labelling a non-JSON body a plain note. CLAUDE.md and AGENTS.md carry the contract, and the packet test matches phrases across line wraps instead of pinning break positions.

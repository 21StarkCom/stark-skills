# CLAUDE.md — stark-skills

## What This Is

The stark skills + tools fleet: a **two-stage development pipeline** (`/stark-author` human-gated spec+plan → `/stark-build` check-gated implementation — no LLM-reviews-LLM loops), PR-finding publication (`/code-review xhigh --fix` reviews; `tools/findings_review_post.ts` publishes the findings on the PR), multi-agent IaC review, and the ops/session tier. Claude, Codex, and Gemini are all enabled (Gemini → `gemini-3.1-pro-preview`, default auth **oauth** — the logged-in Google account's Code Assist seat; `vertex` and `api-key` modes remain via `models.gemini.auth` / `STARK_GEMINI_AUTH`, see `tools/gemini_auth_lib.ts`). The Vertex **project/location are resolved at runtime** by `tools/vertex_config_lib.ts` (env > config > `GOOGLE_CLOUD_PROJECT` > local `gcloud`) — **never hardcoded/committed in source**; in oauth mode the resolved project doubles as the Code Assist licensing project. Note: `-latest` aliases like `gemini-pro-latest` only resolve via the Generative-Language API-key fallback, **not** Vertex. Hierarchical config (global → org → repo).

## Operating Principles

This is a **personal playground**, not production. No customers depend on it; the only user is the author.

- **No rollout ceremony.** Skip soaking, gating, smoking, canary, and gradual-rollout patterns. Merge straight to main once the PR is green.
- **Branch + PR for everything — nothing lost.** Every change lands on a branch and merges via PR; never commit or push to `main` directly. "Ship straight to main" means merge once green, not bypass the PR. Every review's findings get posted on the PR as comments (inline where anchored, summary otherwise; `tools/findings_review_post.ts`, over `review_post_lib.ts::postReview`, does the GitHub posting). Don't drop, downgrade, or summarize findings away, and don't merge with open findings unaddressed — fix them, or reply on the thread saying why not.
- **Every PR action uses `gh` as `aryeh-stark`.** This includes review posting and release operations. Review text identifies the model; authentication never changes with model choice. Both the canonical and Codex-mirror dispatch libraries strip ambient credentials from Gemini environments while keeping the process-variable floor (`USER` included); reviewer subprocesses also exclude database connection strings. Review Apps are retired. CI alone uses the separate `stark-meridian-ci` App in `marketplace-sync.yml`.
  - **The one human-invoked swap: `idun user` (STARK-2215).** When `aryeh-stark`'s GraphQL/REST bucket runs dry, Aryeh can move `gh` to a relief account for the rate-limited command — `export GH_TOKEN=$(idun user --swap)`, with `idun user gh seed|remove|status` managing the Mímir-sourced slots. It is his call, never an agent's — no tool, skill or hook may invoke it. Wiring it into an automated path would re-author whatever ran next, which is exactly the failure this rule exists to prevent. Default stays `primary` = `aryeh-stark`; revert with `unset GH_TOKEN GITHUB_TOKEN STARK_GH_USER` when the window closes. (The `/stark-gh-user` skill + `tools/user_token*.ts` were retired here — `idun user` is a strict superset.)
- **Draft PRs by default — test locally, un-draft to merge.** Every PR-opening path opens a **draft** so WIP stays out of draft-guarded CI while you verify locally. The default is owned by the `gh` path — `idun gh pr-open` resolves it through idun's shared draft config so `pr-open` and `pr-merge` agree on one answer; the review/author/build skills pass `--draft` explicitly. Opt out per-run with `--ready` (alias `--no-draft`). **You cannot merge a draft**, so the merge paths un-draft first: `idun gh pr-merge` (`gh pr ready`) marks the PR ready-for-review — which fires the target CI via the `ready_for_review` event — then wait for green, then squash-merge. For "no CI on WIP" to actually hold, each target repo's `pull_request` workflows need the **skip-draft guard** (`if: github.event.pull_request.draft == false` + `ready_for_review` in `types`) — pattern + `== false` vs `!= true` guidance in `standards/workflows/skip-draft-guard.md`. Push-triggered publishers themselves are unguarded, but their downstream PRs remain drafts until the mandatory head review completes.
  - **NEVER guard a workflow whose check is a required status check.** A guarded job reports `skipped`, GitHub counts `skipped` as *satisfying* a required check, and the merge box renders it identically to a pass — so the guard turns "CI did not run" into "CI is green" over a suite that never ran against what landed. **There is no repair once it happens** — re-running replays the original payload (so it skips again), and a `workflow_dispatch` run **does not join the PR's status rollup** (`test: SUCCESS` in `gh run list`, `test: SKIPPED` in the rollup every merge gate reads). Only a new commit clears it. `.github/workflows/tests.yml` is therefore deliberately unguarded (and carries `cancel-in-progress: false`, since an unguarded job is long enough for the un-draft to cancel the in-flight run and leave `test: CANCELLED` — which GitHub counts as *failing* — on the head sha), and it runs the `tools/` suite.
  - **`main`'s required checks live in a RULESET, not branch protection, and there are four of them.** `gh api repos/21StarkCom/stark-skills/branches/main/protection` returns `404 Branch not protected` even though `main` is gated — that endpoint does not report rulesets, so auditing required checks by reading `branches/*/protection` concludes every repo in the fleet is wide open. Read `repos/O/R/rulesets` (config) or `repos/O/R/rules/branches/main` (what is actually enforced on the ref). Ruleset **20607400 "Required CI on main"**, `enforcement: active`, requires `Analyze (go)`, `Analyze (javascript-typescript)`, `test`, and `typecheck`. The last two come from `tests.yml`; the two `Analyze` contexts come from GitHub's repo-level code-quality setup — a server-side **dynamic** workflow (`dynamic/github-code-quality/codeql`), **not** a file in `.github/workflows/`, so there is no `codeql.yml` here to grep for and its absence proves nothing. A `PUT` to a ruleset replaces its parameters **wholesale** — read, append, write back, or you silently drop a gate while appearing to add one. `sync` (marketplace publish) is deliberately NOT required.
  - **A required check whose step carries `continue-on-error: true` is not a gate.** It reports SUCCESS whether the step passed or not, so requiring it satisfies the merge gate unconditionally — a false green wearing a different hat than the skipped-check one. `typecheck` sat in exactly that trap until STARK-5008: it was excluded from the ruleset because it was advisory, and advisory because of the flag, while `node --test` cannot catch a type error at all (Node **strips** types rather than checking them, so a wrong generic or unsound cast passes the whole `test` job). Both halves were fixed together — the flag dropped, then the context required. `tools/typecheck_gate.test.ts` pins the shape: no `continue-on-error`, no `if:` at **job or step** level (a guarded step leaves the job green with nothing run), no job-level `name:` (it renames the check-run away from the required context, which then never reports), `cancel-in-progress: false`, no `paths`/`paths-ignore` filter and `types:` still carrying `opened`+`synchronize` (no run means no report), and the exact job set — so adding a third job to `tests.yml` fails the suite until someone decides whether its check is required. The step runs `npm run typecheck`, never `npx tsc`: with no TTY, `npx` downloads a missing package rather than failing, which would silently move a required gate onto an unpinned latest TypeScript.
  - **`idun gh pr-merge` refuses a skipped required check**, more strictly than GitHub does, naming it and telling you to push a commit; `--allow-skipped-checks` opts back in for repos that skip a required check by design (path filters). The GitHub PR tooling (`pr-open`/`pr-merge`/`cleanup`) lives in **idun** (`idun gh …`) as of STARK-2211 — its internals are documented there, not here.
- **Language preference:** Go for backend, TypeScript for scripts. **Avoid Python at all costs** — the repo's tooling is TypeScript-only (`tools/`). Do not introduce new Python.
- **Test live.** Local-only verification is not enough. If a flow touches GCP, exercise the real GCP surface.
- **Always update documentation.** Any change that affects behavior, structure, commands, env vars, or operations must update the relevant docs (this file and `AGENTS.md` included) in the same change.

## Distribution

This repo is the **source of truth** for the skills + tools. Distribution is **marketplace-only** — there is no local symlink install step.

- **bifrost** (the marketplace) — the `bifrost` repo packages these skills as separate self-contained Claude Code and native Codex plugins. Claude installs with `/plugin marketplace add 21StarkCom/bifrost` then `/plugin install <bundle>@bifrost`; Codex installs with `codex plugin marketplace add 21StarkCom/bifrost` then `codex plugin add <bundle>@bifrost`. Canonical `skill/` and shared assets remain Claude-authored. Complete Codex variants live only under `runtime-overrides/codex/`, which Bifrost imports into a separate `dist/codex-plugins/` package surface; Codex overlays must never enter `dist/claude/`. `marketplace-sync` prepares versioned release notes and opens a draft Bifrost sync PR. It waits up to 20 minutes for `aryeh-stark`'s completed review attestation on the exact head, then runs the ready/CI/merge chain. CI alone never authorizes publication. For Bifrost's automated sync PRs, the final `aryeh-stark` review body starts with `<!-- stark-code-review:complete -->` on its own first line and names the actual `/code-review xhigh --fix` invocation, added only after the command completes and every finding is fixed or answered; the publisher checks the latest submitted operator review on the exact head, waits for CI, then rechecks the attestation before merging that head. Every changed runtime advances Bifrost's root release version, including Claude-only changes.
- **Local dev is not live.** Editing a file in this repo does not take effect until the change is published (merge to `main` → `marketplace-sync` PR → merge) and the plugin is reinstalled/updated (`/plugin update …`). To test an in-progress edit against a real install, run `stark sync` in the marketplace repo and `/plugin update` locally.
- **Assets plugins don't cover** (user `~/.claude/settings.json`, statusline, output-styles, mutable-state dirs, git hooks) are managed by hand, with one exception: the `~/.claude` symlinks into this repo (`code-review/*`, the statusline scripts, `output-styles/*.md`) are provisioned and healed by `idun clean` from its `ASSET_SYMLINKS` table (`idun/src/clean/clean_lib.ts`). Adding or retiring one of those files means changing that table in lockstep, or `idun clean` re-creates a retired link while a checkout still holds the target and errors on it once the target is gone.
- **GCP worktree scope stays local and narrow.** `tools/gcp_scope.ts install` owns each mapped repo's generated `.envrc` block and the exact `.envrc` row in `.worktreeinclude`; `check` validates both. Other include rows and comments survive, and the tool never adds credentials or broad globs. Codex-managed worktrees consume `.worktreeinclude`; helpers that create plain Git worktrees must copy those named files themselves.
  - **A built-in Claude worktree needs the copied `.envrc` trusted (STARK-5090).** `claude -w` copies `.worktreeinclude` entries but never `direnv allow`s the copy, and direnv keys its allow-list by path **and** content hash — the main checkout's grant covers neither the copy nor a later edit — so a gcp-scoped worktree opens with `.envrc is blocked` and no per-repo scope. `config/settings.json`'s third `SessionStart` hook grants it. Three deliberate limits: it resolves the **worktree root** from the session cwd (a session started in a subdirectory still trusts the root `.envrc`, which `direnv allow .` would have missed); it requires that root to be a real linked git worktree (`.git` is a file), so a directory merely *named* `.claude/worktrees/<x>` in some checked-out tree is never auto-trusted; and `matcher: startup` keeps it off `resume`/`clear`/`compact`, so an `.envrc` edited mid-session still needs a human `direnv allow`. It arrives via `setup.sh`, but only since STARK-5223: the template used to merge *under* the live `~/.claude/settings.json` with a shallow `jq '.[0] + .[1]'`, so a live file that already carried `hooks` kept its own and never gained a template hook — this one included. setup.sh now unions hook entries per event, keyed on (matcher, command list).

**The plugin-resolution seam:** `tools/asset_root_lib.ts` — `assetRoot()` resolves immutable assets (tools/prompts/config) from `${CLAUDE_PLUGIN_ROOT}` when running inside an installed plugin, falling back to `~/.claude/code-review` for direct (non-plugin) invocations through that symlink; `stateRoot()` always stays under `$HOME`. Skills mirror this with `${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/code-review}`. **Never hardcode `~/.claude/code-review/{tools,prompts,scripts,standards}` in a skill or tool** — route immutable-asset reads through `asset_root_lib`/the dual-fallback so plugin installs keep working.

### Dispatchers & orchestration
- `tools/copilot_land_lib.ts` (pure) + `tools/copilot_land.ts` (CLI) — `/stark-build`'s create-or-adopt **impl-PR landing** helper (`branch-name`/`prepare-branch`/`land`): deterministic `copilot/<slug>` branch (name is legacy — the tool outlived `/stark-copilot`, which it originally served), push never `--force`, adopt-or-open PR by head ref (draft by default, `--ready` un-drafts even an adopted draft via `gh pr ready`), multi-PR union. **`prepare-branch --require-base <sha>`** closes a silently-wrong-run class: with no local branch but an existing remote one, the adopt path runs `git checkout -B <branch> origin/<branch>`, which **resets HEAD onto the remote branch** — so a leftover branch from an abandoned run replaces the caller's pinned base with an older codebase while the tool still reports `ok: true`. The flag refuses that adoption **before** the destructive checkout on **both** the `checkout-track` and `checkout-ff` paths (the worktree never moves — a stale *local* branch is as dangerous as a stale remote one) and re-asserts `HEAD` contains the base afterwards. Guardrails: an **empty** value is rejected rather than silently disabling every guard; **unknown flags are a hard error** (a typo like `--requirebase` must not parse to a no-op and disable the guard invisibly); `--dry-run` evaluates the guard and reports `would_refuse` instead of green-lighting the case the real run refuses; and containment is **tri-state** — `merge-base --is-ancestor` exit 128 means *unresolvable* (a `--single-branch`/`--depth` clone never created `refs/remotes/origin/<branch>`), NOT stale, so operators aren't told to delete healthy branches holding pushed work. **`/stark-build` Phase 1 passes it.** Phase 1 additionally checks `prepare-branch`'s **exit code** and that HEAD is on the expected branch: a refusal leaves HEAD untouched, so a bare `merge-base --is-ancestor` compares the base to itself and passes.
- `tools/findings_review_post.ts` — posts a `ReportFindings` payload as one anchored `COMMENT` review through the operator's existing `gh` login. Two divergences from git worth knowing. The parser is **not** a gitattributes parser — it reads `linguist-generated` Set (`=true` or bare) and skips everything else (`-`/`!`/`=false` rows, `[attr]` macros) rather than guessing at last-match-wins precedence. And a slash-less declared pattern like bifrost's `index.json` stays **root-anchored** instead of git's basename-at-any-depth, because basename matching would swallow the hand-written `web/src/__fixtures__/index.json` whose findings ARE fixable where they are posted. **Fail-open, never fail-narrow:** an absent, unfetchable or generated-row-free `.gitattributes` falls back to the configured default, warns on stderr, and never yields an empty list — an empty list is a silent disable, which is the exact failure this path exists to stop. Disabling stays explicit (`--no-generated-split`, or `generated_paths.enabled: false`). The resolved layer is reported as `generatedPathSplit.source` alongside `added` and `warnings`. Two hardening rules the review added: `generated_paths.enabled: false` is a GLOBAL default, so an explicit `--generated-paths` outranks it (only `--no-generated-split` disables a run the operator gave globs to), and a non-array glob list in config (`"default": "vendor/**"`) is refused rather than spread into the one-character globs `["v","e","n",...]`, which match nothing — a silent disable wearing a config typo's hat. The `.gitattributes` read is pinned to the PR head (falling back to the default branch for fork PRs, whose head sha the base repo does not carry), a 403/rate-limit is warned about differently from a plain 404 because only the first means the fallback list may be wrong for this repo, and every declared slash-less pattern this tool root-anchors is disclosed as `generatedPathSplit.rootAnchored`. (The old hardcoded list earned this: `.claude-plugin/**` was missing from its first cut, leaving `marketplace.json` — the one file *every* sync rewrites — still opening a gating thread.) `/code-review --comment` applies **no** split at all, so on a shared publish branch findings must be posted through this tool. Replace the globs with `--generated-paths`, extend them with `--add-generated-paths`, disable with `--no-generated-split`. **Two ways to turn the split off silently are both hard errors** (`--add-generated-paths` is held to the same rule; there an empty value would be a silent no-op rather than a silent disable, which is how a repo's extra generated path ends up back on a gating thread), since a silent disable is the exact failure this exists to stop: an *empty* `--generated-paths` value, and a value that is itself a flag — `--generated-paths --dry-run` used to parse to the glob list `["--dry-run"]`, matching nothing so every generated finding regained its gating thread, while swallowing `--dry-run` so the review really posted. `-` stays legal; it is `--findings`' documented stdin value. That brevity is deliberate: a review body has a hard 65,536-char GitHub ceiling and this split is what moves N findings into it, so the cap is handled — **by `postReview` itself, which degrades rather than refusing (STARK-6094; see its entry above)**. - `tools/review_post_lib.ts` + `tools/finding_lib.ts` — **the survivors of the `/stark-review` burial (STARK-6098** — nastrond grave `graves/stark-skills/stark-review`). `finding_lib.ts` is the pure finding model (`Finding`/`Severity`/`AgentName`, `findingId`, the severity ladder, `buildMarker`), imported by `findings_review_post.ts` and the three `agent_*.ts` ports that `/stark-jury` drives. `review_post_lib.ts` is the REST `gh` transport (`ghJsonOnce`/`ghJson`, HTTP-stream + concatenated-JSON parsers, `withRetry`) plus `postReview` — lifted verbatim, because it is how findings reach a PR. **Two behaviours worth not breaking, both pinned by `review_post_lib.test.ts`:** the **no-drop 422 fallback** (GitHub rejects an anchor outside a diff hunk → demote that comment to the body and retry → on a second 422 demote every anchor; the finding survives, the anchor is what's negotiable) and the **marker-aware retry** (re-read the review marker before each retry, so a successful-but-unacknowledged POST short-circuits instead of double-posting). **A third, added by STARK-6094: the oversize-body degrade.** `GITHUB_REVIEW_BODY_MAX` (65,536) and `GITHUB_ISSUE_COMMENT_MAX` live here, not in a caller, because every caller inherits the failure — over the cap the POST 422s on `body is too long` with **no `errors[].index`**, so the no-drop fallback folds the remaining inline comments into that *same* body, retries it larger, 422s again and reports `unposted`: every finding lost, not one. `postReview` now **degrades instead of failing or refusing**: `planBodySplit` keeps the longest severity-desc prefix of body findings that fits (the input is already sorted by `partitionInlineVsBody`, so the split is deterministic for a fixed payload), and the remainder is posted **in full** as follow-up issue comments on the same PR, cross-linked from the review body. Nothing is dropped, truncated or summarized. **Two shapes moving findings cannot fix are handled too (STARK-6116).** (1) A single finding larger than an issue comment used to get "its own comment rather than being cut" — and that comment then 422d on `body is too long`, `syncOverflowSlot` caught it and the run reported `unposted` with the review never posted: every finding lost to protect one. It is now **segmented** across consecutive comments (`segmentChunks` / `splitTextToFit`; an `OverflowChunk` with a `segment`), each under the cap and each headed `segment i of N` plus the finding it belongs to, so a reader landing mid-way knows where they are. Concatenating the segments after `OVERFLOW_SEGMENT_DELIMITER` reproduces the rendered finding **byte for byte** — a cut with its continuation posted next to it is a page break, not a truncation. Cuts prefer a newline in the back half of the window and never split a surrogate pair. (2) A body whose NON-finding parts are over the cap: `planBodySplit` now computes the floor (every finding out) and returns `unfittable` instead of a plan known to 422. `postReview` answers by **relocating the summary in full** to the leading overflow comment(s) and leaving `relocatedSummaryStub` behind — its first `RELOCATED_SUMMARY_HEAD_MAX` chars and a pointer that SAYS the rest is elsewhere (`bodyOverflow.summaryRelocated`). Relocation is tried only after moving findings alone has failed, so a summary under the cap is byte-identical. If the floor is over the cap even then (`postingAgentNote` / `agents_resolved` — nothing this function may cut), the run is **refused by name before any POST**: `unposted` + `body_over_cap_without_findings`, in dry-run too, and re-checked on every 422-fallback rebuild before slots are synced, so that pass posts nothing for a review that cannot land (comments an earlier pass already posted stay up and stay listed in `bodyOverflowComments` — this file deletes nothing). The floor is the non-finding body **plus the cross-link footer** for every overflow comment, so the refusal reports `floorChars`, not the body alone — otherwise a payload the footer pushed over reads as "310 chars against a 65536-char cap". Three presentation rules ride along: the footer says what the linked comments *hold* (`overflowSummaryParts` — "the review summary", or "the review summary (overflow 1–k) and the remaining findings"; with nothing relocated it is byte-identical to STARK-6094's), because once the summary is out every finding may fit in the body and "carry the remaining findings" is then false; `relocatedSummaryStub` **closes a code fence its head was cut inside of**, since an open fence swallows the pointer, the findings and the overflow links into one code block (segments get no such repair — byte-for-byte outranks rendering); and a finding is sized against the part number it would hold **alone**, because 9 → 10 adds a digit and a finding at exactly the cap as part 9 is one char over as part 10. That replaces the old outcome — 422 with no index → inline comments folded into the same body → larger → 422 → an `unposted` that named nothing. `findingsInOverflow` counts a segmented finding once. Four things worth not breaking: a payload **under** the cap is byte-identical to the pre-STARK-6094 build (the `overflowLinks` footer is only rendered when there is overflow, so no new headers and no reordering); overflow comments are **slot-addressed** — chunk *i* always lives in the same comment, PATCHed in place when a rebuild changes what is in it. Content-addressing reads as equivalent and is not: the 422-anchor fallback merges the demoted findings in and **re-plans**, which shifts which finding lands in which chunk, so every shifted chunk misses the cache and gets a SECOND comment carrying findings already on the PR while the first is left linked from nowhere and `bodyOverflow.chunks` counts one comment where two exist (measured: 2 comments for `chunks: 1`, 5 findings posted twice, 1 orphan). That rebuild also **re-sorts** the merged list: `partitionInlineVsBody` sorts each list severity-desc, but a concatenation of two sorted lists is not sorted and the split keeps the longest **prefix**, so an appended demoted `critical` was pushed into an overflow comment while `low` findings kept the body; a failed overflow POST sets `unposted` and **does not post the review**, because a review whose cross-links point nowhere is the data loss wearing a green hat; and `dryRun` plans the split and reports it under `bodyOverflow`/`bodyOverflowComments` without touching the network. The footer budget the split plans against is a **true** upper bound only because `overflowLinkFor` clamps the link — an `html_url` longer than the per-link reserve is discarded for the canonical `#issuecomment-<id>` form, bounded by GitHub's own owner/repo name limits. Don't "fix" an overshoot by moving findings out of the body: each one moved adds a whole new link line, so that loop diverges and empties the body. `check-rest-only.sh` guards both files — the REST-only contract outlived the dispatcher it was written for.

It used to `child.kill()` the direct child only, so whatever a headless claude/codex/gemini had spawned was reparented to init and ran on (and billed) past the bound; measured, every `npm test` left two `sleep 30` with PPID 1 behind, from a test that asserted `run()` *settles* and nothing about what it left alive. The child now spawns **`detached`**, the SIGTERM → 5 s → SIGKILL ladder goes to `-pid`, and the group is tracked through `bounded_spawn_lib.ts::trackGroup`/`releaseGroup` so Ctrl-C still reaches it (detaching without forwarding re-creates the STARK-6135 gap; the ladder stays `run()`'s own, as jury's does). Four things worth not undoing: a **timed-out settle sends the group one SIGKILL** — the leader can exit on SIGTERM and close our pipes while a descendant that ignores SIGTERM lives on, and settling is the last moment anyone holds the group id; the **remaining ladder timers are cleared on settle** — they used to fire after the call was over, harmless against one reaped pid and not against a group id that is free for reuse once the group empties; a **normal close delivers nothing**, for the same reason — a descendant the child left behind was never condemned, so it is spared; and **ESRCH latches**. That last one is the guard the rewrite silently dropped: `child.kill()` is a no-op once the child has exited, while `process.kill(-pgid)` signals whoever holds the id NOW — and clearing the ladder on settle does nothing for a call that has *not* settled. Measured before the latch, with an escaped descendant holding stdout: a leader killed at the timeout drew a SIGKILL at 5 s (ESRCH) and another at settle, 2 s *after* the kernel had said the group was gone; a leader that exited on its own at t=0 drew SIGTERM + 2x SIGKILL at an id freed for the whole length of the timeout — minutes, for a real agent (and this machine's pid counter wrapped between two probes a minute apart). So the first ESRCH ends all signalling, and the leader's `exit` probes the group with **signal 0** — which delivers nothing — while the id cannot yet have been reused. Not caught: a group an in-group descendant keeps alive past that probe and that empties later; there the latch stops at one signal. Not reached: a descendant that `setsid`s out of the group — `run()` still settles past it via the last-resort pipe teardown, which is now the only thing that test can exercise (an ordinary stdout-holding descendant dies with the group). `agent_dispatch_lib.test.ts` runs every tree test against **both** composed trees (canonical, and `tools/` overlaid with `runtime-overrides/codex/tools/`), because the mirror carries its own copy of `run()`; its forwarding tests wait for an ARMED marker, not just the child's pids. Mutation-checked: a direct-child kill fails the descendant test (3 survivors), dropping the settle-time SIGKILL leaves exactly the SIGTERM-ignorer, dropping `trackGroup` fails both signal tests, and dropping `releaseGroup` in the mirror alone fails only the codex tree. The signal-hygiene rules are pinned by recording every `process.kill(-pgid, …)` a call makes (`recordGroupSignals`), each mutation applied to ONE copy and failing only that tree: dropping the latch fails the escaped-descendant and emptied-group tests, dropping the `exit` probe fails the emptied-group test alone (the latch still covers the other through the 5 s rung's ESRCH), and un-guarding the settle-time SIGKILL fails the normal-close test — whose leftover descendant is what keeps the group alive past the probe, since over an empty group the latch would swallow that SIGKILL and the mutation would pass. The cleared ladder is pinned by counting active timers, not signals, for the same reason: the latch hides whatever a stale rung sends.

### Pipeline (end-to-end, in order)

- `/stark-author <intent|notes-path> [--tier skip|short|full] [--out PATH] [--no-advisory] [--ready]` — **Stage 1 (evidence-based rewrite): human-gated spec+plan authoring in ONE session.** Tier check (skip/short/full by uncertainty, not length) → time-boxed recon (~10–15 tool calls) → plain-language interview that asks ONLY operator-oracle questions (outcome, OUT boundary, must-never-happen, genuine product forks) and **never quizzes the operator about files/interfaces — the agent derives those from recon and decides sensible defaults itself, surfacing only genuine product forks (≤3, each carried with its default) for veto at sign-off** → one self-contained doc (`docs/specs/YYYY-MM-DD-<slug>-spec.md`: intent, IN/OUT boundary, non-derivable repo context, EARS criteria, task DAG sized in tens of human-minutes with machine-checkable done-whens, closing verification command, append-only Deviations; plus a NON-normative plain-English operator digest sidecar `docs/specs/YYYY-MM-DD-<slug>-spec.human.md` — **five fixed jargon-free sections** (what it does · what it will NOT do · what the agent checked itself so the operator doesn't have to · where the agent is genuinely unsure · the calls the agent made for the operator), commands glossed in plain words, ≤40 lines Full / ≤15 Short, regenerated on every revision — spec wins on conflict) → **a mandatory dead-simple three-layer intent read-back at the end of authoring** (what you want now · the deeper goal · the point of it all · "did I get it right, or did I miss it?" — replayed until the operator confirms) → at most ONE zero-shared-context advisory subagent pass (findings go to the agent to triage once, never a loop) → **operator sign-off: 3 plain questions only (did I understand you · keep the calls I defaulted · anything I couldn't see from the code) — no quiz, no file-opening, no rubber-stamp tripwires, because the agent already did all technical QA** → pin (`accepted-base` commit hash) → draft PR (`spec/<slug>`, authored by `aryeh-stark` via `gh`) → fresh-session handoff contract. **No LLM-reviews-LLM loop anywhere; all technical verification is the agent's job (Phase 3), never the operator's.** Evidence: `skill/stark-author/references/stage1-dossier.md` (gate deliberately adapted from the dossier's RQ5 for a non-coding operator). Skill `skill/stark-author/SKILL.md` — pure protocol, zero new TS machinery. **Phase 3 carries a wiring-seam checklist.** Before a file set is final, scan four classes of seam without which a task's work is inert: **registration/dispatch** (migration step lists, capability registries, route tables — a migration `.sql` is inert data until the step list runs it), **generated artifacts pinned by tests** (schemas/catalogs/generated docs that adding a struct field makes stale by construction), **call sites** (a new helper with zero callers is dead code behind a green gate), and **doc/description generators** (where the emitted text actually lives). The closing authoring test: *"if this task's diff were applied and nothing else, would the behavior criterion actually hold at runtime?"* A done-when can pass while the answer is no — that is the vacuous-green the whole two-stage design exists to prevent.
- `/stark-build <spec-path> [--dry-run] [--no-advisory] [--no-fix] [--stay-draft] [--max-turns N] [--model ID]` — **Stage 2: autonomous implementation from an accepted `/stark-author` spec.** The interactive session is the RUNNER: it dispatches one fresh headless `claude -p` session per spec task, **gated by checks the agent cannot edit** — a PreToolUse path-deny hook write-protects the spec + gated existing tests + harness scripts (`skill/stark-build/references/hooks/protect-paths.sh`), and a Stop-hook gate blocks turn-end while the task's done-when check is red, flipping to **abort-with-deviation at 7 consecutive blocks** so Claude Code's 8-block override never lands a silent green (`references/hooks/stop-gate.sh`). Abort is a first-class success; anti-cheat prompting is never the gate. Sequential single writer; worktree at the spec's `accepted-base`; branch `build/<slug>` + immediate draft PR via `tools/copilot_land.ts` (create-or-adopt, never force); one commit per green task; crash/timeout = ONE resume from PROGRESS.md + commits, never from zero. The runner verifies every task deterministically (re-runs the check itself, diff-vs-protected-list tamper check, diff-vs-declared-file-set scope check). The spec's closing verification command is a **held-out e2e gate** (task-green/e2e-red divergence = the gaming/mis-decomposition signal; PR stays draft). ONE cross-vendor advisory review (codex, read-only, full diff + spec) posts severity-tagged findings to the PR (pinned `SEVERITY: critical|high|medium|low` ladder so the filter is machine-readable), followed by **Phase 4b — exactly ONE fix round over the medium+ findings** (`--no-fix` opts out): a single fresh headless session under the same hook harness, e2e as its Stop-gate check, told to fix only what the findings name and to *reject* a wrong finding with a logged reason rather than fake it. The runner then re-runs every task check + e2e itself and reverts the fix commit on any regression — **the advisory reviewer is never re-run, there is no round 2, and `low` + anything still open dies at the human**. A rejection is a claim, not a resolution: any medium+ left open keeps the PR draft. Fix-round yield (selected/fixed/rejected/regressed) is the kill-switch metric. State + evidence under `~/.claude/code-review/history/build/<slug>/<run-id>/`, never the repo. Protocol skill + two POSIX hook scripts. Evidence: `skill/stark-build/references/stage2-dossier.md`. Skill `skill/stark-build/SKILL.md`. **Harness rules that keep a false green from landing:** (1) **every dispatched subprocess closes stdin** (`</dev/null`) — both `claude -p` and `codex exec` read stdin *in addition to* the prompt arg, and an orchestrated shell's stdin is a pipe that never EOFs, so `codex exec` hangs on it; the rule covers `stop-gate.sh`'s own check invocation too (a Stop hook's stdin is the payload pipe), while `protect-paths.sh` is the deliberate exception since it must read the payload; (2) task evidence goes to `$STATE/evidence/<id>.log`, never `$STATE/tasks/<id>/` (which `protected.list` blocks); (3) **long gates run backgrounded and stop via task-stop, never a foreground timeout** — a foreground timeout leaks the child tree so each retry competes with its predecessors and reads as external contention; (4) the runner may run the done-when **verbatim and unmodified** when the `bash check.sh` wrapper won't return (determinism holds because the command is identical and still runner-run) — and **macOS has no `timeout(1)`**, so a `timeout`-wrapped sweep reports every gate as a false red in 0s via exit 127; (5) broad kill patterns (`pkill -f "go test"`) match command-line text, not ownership, and can kill the runner's own in-flight gate or a *different* concurrent run's task — scope kills to this run's `$STATE` path; (6) `prepare-branch --require-base` (see its entry above) and Phase 1 asserts the pin independently. Two more that can still land a false green: `protected.list` directory entries carry **no trailing slash** — a trailing slash builds the glob `<dir>//*`, which matches nothing, so the Edit/Write deny branch passes every file under it and a task session could rewrite its own `check.sh` (`protect-paths.sh` normalizes trailing slashes itself, but write them without anyway); and the wrapper-flake fallback runs the check file's **whole content**, never the done-when "verbatim from the spec" — the latter drops the wrapper's `set -euo pipefail; cd <wt>` envelope and greens a task against the **main checkout**. Also: the runner's own gate invocations keep the `bash` prefix (`check.sh` has no shebang and is never `chmod +x` — direct execution is a 126 false red) and close stdin; a hard time bound must kill the process **group** (a signal to just the exec'd shell orphans the `go test` children it should have bounded); and use `pgrep -lf`, not `pgrep -af` — on macOS `-a` means *include ancestors*, which widens the set to the orchestrating session. For implementation from an accepted spec it replaces copilot's review loop, plan-to-tasks, and phase-execute.

### Workflow & Ops

- `/gru start <STARK-epic | --tickets STARK-n,...> [--max-workers N] [--agent claude|codex]` — **Gru** drives an epic or ticket list to done with one `/minion` per ticket: expand the epic via alfred, order by declared dependencies, launch ≤ N Minions with `hermod ticket`, receive `done`/`blocked`/`follow-up` reports over Hermod, confirm each `done` by reading the merged PR and the ticket status, launch the next ready ticket, report when all are finished or blocked. Rerunning `start` resumes from the board; stopping is a plain instruction. Gru grants nothing: a Minion merges once its review gate is green, fixes in-scope gaps in its own PR, and files a follow-up ticket for a whole effort, reports it, and ends. A Minion **verifies live** before opening its PR, **re-runs that check after the `--fix` round and posts the command and its output as a PR comment**, and names it in its `done` report — the comment is the point: stand-down destroys the Minion's scrollback, so a report naming a verification nobody can read is the faith Gru's confirm step exists to refuse. Write the check in the report as prose, never a pasted command line — the report is a double-quoted shell argument. A `done` Minion then **stands down** — `hermod poison-pill --json` (no behavior-changing flags, run strictly after the merge, the ticket close, a clean `git status --porcelain` plus an empty `git log origin/<own branch>..HEAD` — poison-pill skips the dirty/unpushed gate — and strictly after the report so the report is a completed act) exits the agent, removes the worktree and closes the cmux tab in one line, identically on both runtimes since the quit verb is hermod's problem. The unpushed check is against the Minion's **own branch at origin, never `origin/main`**: `pr-merge` squash-merges, so `origin/main..HEAD` is non-empty forever after a perfectly good merge, and a gate that can never go green is a gate that gets ignored. Standing down on a `done` exit is the declared terminal step of the ticket the Minion was handed and needs no go-ahead from anyone — it makes no difference whether Gru launched the Minion or a hand did, and with no leader peer the `done` line is said in-session (the durable evidence is the PR comment either way). The hard scope stays non-negotiable (after merge + ticket close, own tab only, never on `blocked`/stopping, never any other trigger), and the standing Bash permission the command needs is still the operator's. **Never from a subagent**, which shares `$CMUX_SURFACE_ID` and would tear down the parent's tab; a *dead* Minion's tab is reaped with `hermod close-session <surface>`, never poison-pill (poison-pill targets only the caller's own surface; close-session refuses only that one) — and it stays the **operator's** call: Gru reports the surface and does not run it. `armed:true` is the only proof it took — **and it is printed only under `--json`**, which is why the command carries that flag; the ack echoes the validation plan, so a live run prints the same `dry-run: would exit …` detail a `--dry-run` does and `armed:true` is the only thing telling them apart, while a "nothing happened" re-run arms a second reaper. The real outcome is in `$TMPDIR/hermod-poison-pill-<pid>-<stamp>.log`, and the reaper waits for idle. It aims at the **session's recorded cwd** resolved up to the git toplevel, *not* the shell's current directory, so a subdirectory needs `--cwd`, never a `cd` — and the clean-tree checks above must be run against *that* path. A `partial` never self-heals and `--resume` makes it worse by recreating and re-locking the removed worktree, so Gru must never assume a stood-down Minion's worktree is gone — nor its tab: on the claude-lock `partial` (claude holds a git lock on its worktree for the session's life and the reaper refuses to remove one whose lock owner is alive) close-session returns *before* closing the tab, leaving worktree **and** tab behind, while cmux's `Cannot close the last surface` leaves the worktree gone and the tab alive. Both are the operator's to sweep. Branches stay for the operator's `idun gh cleanup`, so no `--delete-branch`; a `blocked` or `follow-up … stopping` Minion does not stand down at all, leaving its worktree and tab for the operator. **A ticket's repo resolves through `frigg repos get`, and a bad `--cwd` is the silent failure (STARK-6186).** `hermod ticket --repo <name>` resolves the name via `frigg repos get` (exit 3 = unregistered), so Gru asks that same question per ticket at launch rather than caching one `frigg repos list` whose answer goes stale the moment the operator seeds a repo mid-run. An unresolvable name (exit 3, or a record whose `stale` is true because its path is gone) falls back to a path — the fleet root taken from a registered record's own `path`, never a hardcoded `~/Code/21Stark`, since the fleet has checkouts under other roots — and that path must be **proved** with `git -C <path> rev-parse --show-toplevel` before it is passed. **hermod does not refuse a `--cwd` it cannot use**: measured, `--cwd /tmp/<missing>` exits 0 with a normal-looking ack and cuts the worktree from the CALLER's repo, so an unproved guess lands the Minion in stark-skills and the ticket is implemented, PR'd and merged in the wrong codebase — invisibly, because step 2's ownership rule matches on the ticket id alone and the claude ack carries no `worktree` field (only Codex's does). Hence the post-launch `hermod msg peers` cwd check on any `--cwd` launch. `--repo` and `--cwd` are mutually exclusive, so the fallback replaces `--repo`. A guess that will not prove out **blocks** the ticket — step 2 classifies it blocked, which is what keeps step 6's loop terminating instead of relaunching it every pass. Seeding the registry stays the operator's: Gru runs neither `frigg repos scan` nor `frigg repos set`, and reports the per-repo `frigg repos set <repo> --path <p>` that hermod's own error names, because `frigg repos scan <root>` cannot reach a checkout outside that root. Both skills have Codex variants under `runtime-overrides/codex/`.

- `/agnes <STARK-n>` — **Agnes: a Minion with no Gru.** The operator launches one tab on one ticket (`hermod ticket STARK-n --repo <repo> --agent claude|codex --prompt-file <brief>`, where the brief is just `/agnes STARK-n`) and walks away; Agnes carries it end to end and poison-pills herself when it is done. Removing Gru removes three guarantees and Agnes supplies each herself: **nobody confirms her `done`**, so `gh pr view <PR> --json state,mergeCommit` + `alfred task show STARK-n` is a mandatory phase gating the stand-down (a failed confirmation is NOT a stand-down — comment what came back wrong and stop with the tab alive); **nobody sequences merges**, so an `idun gh pr-merge` refusal is answered with a rebase and a rerun, never a force and never a wait; **nobody to report to**, so there is no `hermod msg` at all and the ticket comment (PR link, merge sha, the live verification command and its output) is the only report surface. A brief naming a leader peer means she is the wrong skill — say so and stop, that is `/minion`. Blocked or a stopping follow-up leaves the tab and worktree for the operator — an unattended worker is exactly where “clean up anyway” is tempting. Codex override in lockstep, and it matters more here than for a Gru-led Minion: `hermod ticket` refuses an existing Codex worktree, so an Agnes who fails to stand down blocks her own relaunch.

So the live number is always shown **without a restart**; the payload is the fallback, not a co-displayed second value. The daemon read is fork-free (slurp the file, slice the current seat's object by its `"<seat>": {` opener, regex `fivePct`/`weekPct` out of the flat body); the `== *"<seat>": {*` presence guard is load-bearing — a missing seat would otherwise leak the WHOLE file into the slice and surface a **different** seat's percentages, and one account can hold seats in two orgs at once (same `accountUuid`, different `organizationUuid`), so the wrong-seat number is a live hazard, not hypothetical. ## Conventions

- **Docs live with the code** under `docs/`, folder per type — `adr/` (`NNNN-<topic>.md`, immutable: supersede, don't edit), `specs/` (`YYYY-MM-DD-<topic>-spec.md`), `retros/` (`YYYY-MM-DD-<topic>-retro.md`). **This is the layout `/stark-init-docs` scaffolds into a target repo, and `tools/doc_convention.test.ts` guards that scaffolding — it is not a layout this repo keeps.** stark-skills itself carries no `docs/` tree: every skill is documented by its own `SKILL.md` and its `--help`. **There is never a `docs/plans/`** — the spec carries the plan (task DAG, per-task done-whens, closing verification command), which `/stark-build` consumes.   prompt corpus is gone** — it was `/stark-review`'s and was buried with it

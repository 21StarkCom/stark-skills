## What This Is

The stark skills + tools fleet:

- **A two-stage development pipeline** — `/stark-author` (human-gated spec+plan) → `/stark-build` (check-gated implementation). No LLM-reviews-LLM loops, per the 2026-07-25 autopsy.
- **PR finding publication** — `/code-review xhigh --fix` is the review; `tools/findings_review_post.ts` publishes its findings on the PR as ONE anchored review.
- **Multi-agent IaC review** — `/stark-terraform-review`, `/stark-terragrunt-review`.
- **The ops/session tier** — session, handover, release, persona, GitHub identity swap.

Claude, Codex and Gemini are all enabled (Gemini → `gemini-3.1-pro-preview`, default auth `oauth`). Vertex project/location resolve at runtime via `tools/vertex_config_lib.ts` — **never hardcoded or committed**. Hierarchical config: global → org → repo.

## Operating Principles

This is a **personal playground**, not production. No customers depend on it; the only user is the author.

- **Branch + PR for everything — no exceptions.** Every change lands on a branch and merges through a PR. **Never commit or push to `main` directly.** "Ship straight to main" means *merge once the PR is green* — it does **not** mean bypass the PR. (This file said "Ship straight to main" with no branch+PR rule until 2026-08-07. That was wrong, and it was wrong only for you — Claude read the correct rule the whole time.)
- **No rollout ceremony.** Skip soaking, gating, smoking, canary and gradual-rollout patterns. Merge once green.
- **Every review's findings get posted on the PR.** Inline where anchored, summary comment otherwise — `tools/findings_review_post.ts` (over `review_post_lib.ts::postReview`) does the posting. Don't drop, downgrade or summarize findings away, and don't merge with open findings unaddressed: fix them, or reply on the thread saying why not.
  - **Except on generated paths, which get a body entry instead of a thread** (STARK-5637). `tools/findings_review_post.ts` reports a finding whose only anchor matches a generated-output glob in the review **body**, carrying the file and line it would have anchored to, plus the glob that matched and a preamble saying why. The list is **resolved per run from the target repo** (STARK-6095), highest layer first: `--generated-paths` > the `generated_paths.repos["O/R"].paths` config entry > the target repo's own `.gitattributes` `linguist-generated=true` rows > `generated_paths.default`. `--add-generated-paths GLOB,...` EXTENDS the resolved list instead of restating it; `--generated-paths` still replaces; `--no-generated-split` (or `generated_paths.enabled: false`) disables. `generated_paths.repos` ships EMPTY (STARK-7536): the one entry it carried, `catalog/**` repo-keyed to bifrost, went when bifrost started declaring its own generated catalog trees (`catalog/standards/**`, `catalog/*/skills/**`, `catalog/*/commands/**` — STARK-7363), since the wildcard was broader than what is generated and also demoted the hand-authored `catalog/*/bundle.yaml`, `catalog/*/mcp/**` and `catalog/*/agents/**`. A catalog glob still must never reach the global default — a hand-written `catalog/` elsewhere must keep its threads. Accepted cost: `bundle.yaml`'s sync-written `version:` bump is no longer demoted, so use `--add-generated-paths 'catalog/*/bundle.yaml'` on a sync-PR run that draws a finding there. The reader takes `linguist-generated` Set only (`=true` or bare) and refuses to guess at negation, `=false` or `[attr]` macros; a slash-less declared pattern stays root-anchored rather than git's basename-at-any-depth, so `web/src/__fixtures__/index.json` keeps its thread. An absent or unreadable `.gitattributes` falls back to the configured default and warns on stderr — it never narrows the list to nothing, because an empty list is a silent disable. Both silent-disable routes are refused rather than parsed: an *empty* value, and a value that is itself a flag (`--generated-paths --dry-run` used to mean the glob list `["--dry-run"]` — matching nothing — while swallowing `--dry-run`, so the review really posted). An assembled body over GitHub's 65,536-char review-body cap no longer refuses (STARK-5637) and no longer loses every finding (the 422 carries no index, so the fallback folds the inline comments into the same body and fails larger): **`postReview` degrades** (STARK-6094). The cap constants live in `review_post_lib.ts` so every caller inherits it; the highest-severity findings that fit stay in the review body, and the rest are posted in full as cross-linked follow-up comments on the same PR. A single finding too large for one comment is **segmented** across consecutive comments that reassemble byte for byte, and a summary that alone blows the cap is **relocated in full** with its head and a pointer left in the body (STARK-6116) — but only when that is genuinely a degrade (STARK-6245): the stub must be shorter than the summary *and* the relocated plan must fit, since the leading summary chunks add footer reserve of their own, so a refused plan is never a relocated one. A body still over the cap with nothing left to move is refused by name (`body_over_cap_without_findings`) before any POST. Nothing is dropped or truncated, the split is deterministic, and a payload under the cap is byte-identical to before. **`/code-review --comment` has no such split** — on a shared publish branch, route findings through this tool instead. Why: on bifrost#264, 34 inline threads on `vendor/**` and `dist/**` held the PR at `BLOCKED` with all five checks green under `required_conversation_resolution` — and `auto/marketplace-sync` is **shared**, so they blocked a *different* session's publish. They were unfixable where posted: a regenerated snapshot of code already merged upstream, hand-edits rejected by the drift gate, tree overwritten by the next sync. The mechanism drops generated files from the `changedFiles` set `postReview` partitions against, so nothing is dropped, downgraded, re-classified or auto-resolved — **only the gating thread is withheld**. Globs match the whole repo-relative path, never gitignore's basename rule, so hand-written fixtures like `web/src/__fixtures__/index.json` keep their threads. **Never auto-resolve someone else's thread**: a finding is dispositioned by its author, not by a publisher who wants to merge. And `required_conversation_resolution` is correct — it stays; bifrost hides it in *classic* protection (`/branches/main/protection`), which `rules/branches/main` does not surface, the exact inverse of this repo. **Those body entries get their own heading, not the out-of-diff one** (STARK-6096): `Finding.body_reason` lets the caller say WHY a finding is in the body — `buildReviewBody` cannot tell a withheld in-diff finding from a genuinely out-of-diff one by file/line — and the renderer groups on it, so a generated-path finding sits under "Findings on generated paths — withheld from inline threads" instead of a heading claiming it was outside the PR's scope. That heading claims **in-diff** no more than out-of-diff, deliberately: a reviewer can report a finding on a generated file the PR never touched, and the per-finding note is what states which case an entry is. Labelled groups render first so the generated-path preamble is not separated from the findings it introduces; findings with no `body_reason` still render byte-identically to before (one group is one heading and one pass whichever end it is emitted from), so every other caller is untouched. Two no-drop rules: an unrecognised `body_reason` degrades to the unlabelled group rather than forming a heading-less group the renderer would skip, and a 422-demoted inline comment loses its label on the way into the body.
  - **A killed `gh` names its cause on both paths** (STARK-371 read path, STARK-6112 posting path). `tools/child_termination_lib.ts::explainTermination` is the one shared helper — cause first, so it survives the callers' 400-char slice. `review_post_lib.ts::ghJsonOnce` treats a signal-killed `gh` as a failure **before** parsing its stdout: a `--paginate` killed between pages would otherwise parse as a clean, truncated 200. A non-zero exit behind a 2xx is refused the same way (a later page died at the transport), and `spawnBounded` listens for `child.stdin` errors so a `gh` killed before draining a large POST body reports its cause instead of crashing the tool on an uncaught EPIPE. The cause lives in `GhError.body` too — `postReview`'s `unpostedReason` reads the body, not the message.
  - **And a hung `gh` is bounded** (STARK-6113): 120 s on both spawn paths, override with `STARK_GH_TIMEOUT_MS` (ms; an unusable value is a hard error, never "unbounded"). Measured, not guessed — an 855-file / 7.1 MB paginate took 6.7 s. SIGKILL, never settling a timed-out call on `close`, and the cleared timer are each load-bearing; see `CLAUDE.md`.
  - **The kill reaches `gh`'s whole process group** (STARK-6131). Both paths spawn through `tools/bounded_spawn_lib.ts::spawnBounded` — `detached`, group SIGKILL on timeout and on `maxBuffer` — so nothing `gh` spawned is orphaned. `detached` takes `gh` out of the terminal's foreground group, so the lib forwards SIGINT/SIGTERM/SIGHUP to every live group and re-raises: Ctrl-C still works. It re-raises only when its listener is the sole one — a tool with its own handler already got that delivery, and re-raising handed it one Ctrl-C twice. Not bought back: `detached` is a new *session*, so a supervisor's group-SIGKILL of the tool no longer reaches `gh`. `runCapturing` and its `RunFn` are async as a result; `spawnSync` can do neither half. **`spawnBounded` also latches ESRCH and listens on the read pipes** (STARK-6245): the group is never signalled once the kernel says it is gone (the leader's `exit` probes it with signal 0, and the latch also untracks so `forward` cannot deliver the same recycled-id signal by the other door), and a `stdout`/`stderr` failure is reported as a termination — `status: null` plus a named cause, never a truncated stdout under a clean exit code. **Since STARK-6735 the claim on a group is keyed by call, not id**: `makeGroupKiller` is the one door (claim + latched signaller + that call's release; `trackGroup`/`releaseGroup` are gone), `forward` shares the per-call latch so a group that empties after the exit probe is signalled once rather than once per Ctrl-C, jury's seats take the same door with an exit probe so an emptied seat leaves the forwarding set at once instead of at `emit`, and `run()`'s last-resort result reports the leader's real exit and only a signal the kernel accepted — never an invented SIGKILL. `spawnBounded`'s timeout result follows the same rule (`signal` is `SIGKILL` only when the kernel accepted it, else the leader's real `signalCode`; `status: null` + `error` still say the bound fired), and jury's skipped ladder still files an `attempted: false` kill report naming why nothing was sent. **`forward` reads its sole-listener check BEFORE it signals**: a latch that trips on the last claim untracks, removing `forward`'s own listener mid-delivery, so read afterwards an embedding tool's handler looked sole and drew the re-raise — the two-deliveries failure above, reintroduced by the latch. See `CLAUDE.md`.
  - **`/stark-jury`'s seats get the same forwarding** (STARK-6135). `jury_dispatch.ts::realRunner` detaches its seats too; it claims each seat's group through `bounded_spawn_lib.ts::makeGroupKiller` (was `trackGroup`/`releaseGroup` until STARK-6735), so Ctrl-C reaches an in-flight seat and its descendants. Jury keeps its own SIGTERM → grace → SIGKILL ladder; only the tracking is shared. The lib refuses group ids `<= 1` (`-0` is the tool's own group, `-1` every process the user owns) through one exported predicate, `isSignallableGroup`, which jury's `killProcessGroup` imports rather than restating. Test-writing trap: a child reporting its pids does **not** mean forwarding is armed — under a parallel suite it can write them before the tool gets from `spawn()` to the claim, and a signal landing there kills the tool by default disposition (so "died by the signal" passes vacuously) and orphans the child. Both files' forwarding tests wait for an armed marker instead; see `CLAUDE.md`.
  - **`agent_dispatch_lib.ts::run()` is the third spawn path and gets both halves** (STARK-6147). It backs `iac_review_lib.ts` and `refactor_planner_provider.ts` — headless claude/codex/gemini, which spawn children and bill while alive — and its timeout used to `child.kill()` the direct child only. It now spawns `detached`, sends its SIGTERM → 5 s → SIGKILL ladder to the **group**, and claims the group through `makeGroupKiller`. On a timed-out settle the group gets one SIGKILL (the leader can die on SIGTERM and close the pipes while a descendant ignoring SIGTERM lives on) and the remaining ladder timers are cleared; a normal close delivers nothing, sparing whatever the child left behind. **ESRCH latches**: unlike `child.kill()`, which is a no-op once the child has exited, `process.kill(-pgid)` signals whoever holds the id now, and clearing the ladder on settle does nothing for a call that has not settled — with an escaped descendant holding stdout, a leader that exited at t=0 drew SIGTERM + 2x SIGKILL at an id freed for the whole timeout. So the first ESRCH ends all signalling, and the leader's `exit` probes the group with signal 0 (delivers nothing) while the id cannot yet have been reused. The latch is the shared `bounded_spawn_lib.ts::makeGroupKiller` (STARK-6377), not a private copy: three copies drifted within a day — STARK-6245 taught `spawnBounded`'s to `releaseGroup` on ESRCH (or `forward` delivers the recycled-id signal by the other door) while both `run()` copies kept the bare latch — so all three now take the killer from one factory, pinned in both trees by "a group the kernel has reclaimed is untracked while run() is still open". Settle paths release through the killer (`killTree.release()`), never by id: an id-keyed release is idempotent per id, and an id the latch already let go may belong to a concurrent call's child by then — releasing it by id would leave that live agent deaf to Ctrl-C. Jury takes the same door since STARK-6735 (exit probe, and its ladder is skipped once `gone`), and `run()`'s last-resort result no longer invents a SIGKILL. Not reached: a descendant that `setsid`s out of the group — `run()` still settles past it (the last-resort pipe teardown). The Codex mirror `runtime-overrides/codex/tools/agent_dispatch_lib.ts` carries the same `run()`, and `agent_dispatch_lib.test.ts` runs every tree test against both composed trees.
  - **Rerunning a post is safe** (STARK-6125). A POST can land and still report `unposted` (killed or timed-out `gh`), so `postReview` checks the PR for this payload's marker **before the first write of any kind** — overflow comments included — and on a hit writes nothing and returns `alreadyPosted: true` (exit 0, said on stderr). A failed check refuses rather than risk the double-post — and an unreadable one (a 2xx that is not a JSON array) counts as failed, never as "nothing there", on the reviews list and the issue-comments list alike. Overflow comments orphaned by a truly failed run are adopted into their slots, not re-posted. The marker's run hash now covers the whole payload plus the head sha (`review_post_lib.ts::computeRunHash`, re-exported by `findings_review_post.ts`); the old first-three-ids hash would have let the skip swallow a different review, so any new caller of `postReview` must derive `runHash` with it.
- **Draft PRs by default.** Every PR-opening path opens a **draft**, so WIP stays out of draft-guarded CI. Test locally, then un-draft to merge. Opt out per-run with `--ready` (alias `--no-draft`). You cannot merge a draft, so the merge paths run `gh pr ready` first — which fires target CI via `ready_for_review` — then wait for green, then squash-merge. Target repos need the skip-draft guard for "no CI on WIP" to hold: `standards/workflows/skip-draft-guard.md`.
  - **But never guard a workflow whose check is REQUIRED** (STARK-357). A guarded job reports `skipped`, GitHub counts that as satisfying the required check, and it looks identical to a pass — so the guard turns "CI did not run" into "CI is green". PR #877 merged that way; the suite never ran against what landed. Nothing repairs it after the fact: a re-run replays the original payload and skips again, and a `workflow_dispatch` run never joins the PR's status rollup. `.github/workflows/tests.yml` is deliberately unguarded and runs the `tools/` suite. The merge paths (`idun gh pr-merge`) refuse a skipped required check, naming it; `--allow-skipped-checks` opts back in for path-filtered checks that skip by design.
  - **`main`'s required checks live in a RULESET, and `branches/main/protection` lies about it** (STARK-5008). That endpoint returns `404 Branch not protected` on a repo that IS gated, because it does not report rulesets — audit with `gh api repos/O/R/rulesets`, or `repos/O/R/rules/branches/main` for what the ref actually enforces. Here: ruleset **20607400**, `active`, four contexts — `Analyze (go)`, `Analyze (javascript-typescript)`, `test`, `typecheck`. A `PUT` replaces the rule's parameters wholesale, so read → append → write back; overwriting drops a gate while looking like it added one.
  - **And never require a check whose step carries `continue-on-error: true`** — it reports SUCCESS regardless of the step, so requiring it satisfies the gate unconditionally. `typecheck` was stuck in that loop until STARK-5008 (left out of the ruleset for being advisory, advisory because of the flag) while `node --test` could never catch a type error anyway — Node strips types instead of checking them. Flag dropped, then context required. `tools/typecheck_gate.test.ts` pins the job set plus the absence of `continue-on-error`, of any `if:` (job **or** step — a guarded step leaves the job green with nothing run), of a job-level `name:` (renames the check-run so the required context never reports), and of a trigger/path narrowing; so a third job in `tests.yml` fails the suite until its check is decided. The step runs `npm run typecheck`, not `npx tsc` — headless `npx` downloads a missing package instead of failing.
- **Every PR action uses `gh` as `aryeh-stark`.** This includes review posting and release operations. Review text identifies the model; authentication never changes with model choice. Both the canonical and Codex-mirror dispatch libraries strip ambient credentials from Gemini environments while keeping the process-variable floor (`USER` included); reviewer subprocesses also exclude database connection strings. Review Apps are retired. The `stark-meridian-ci` App's only consumer here was `marketplace-sync.yml`, now deleted (STARK-8248) — no workflow in this repo mints a token, and its App-ID variable / private-key secret are orphaned credentials awaiting removal.
  - **`idun user` is the other exception, and it is human-invoked only** (moved out of stark-skills in STARK-2215). It moves `gh` to a relief account when `aryeh-stark`'s rate bucket runs dry — `export GH_TOKEN=$(idun user --swap)`. **No tool, skill or hook may invoke it** — it exports `GH_TOKEN`, which overrides `gh`'s keyring for every later call in that shell, so an automated swap silently re-authors whatever runs next.
- **Language: Go for backend, TypeScript for scripts.** **No new Python.** The repo's tooling is TypeScript-only under `tools/`; the former Python orchestrators and dispatch infra under `scripts/` were migrated out and deleted. If you find a `scripts/*.py` path named in any doc, it is stale — delete the reference, don't recreate the file.
- **Test live.** Local-only verification is not enough. If a flow touches GCP, exercise the real GCP surface.
- **Update docs in the same change.** Any change to behavior, structure, commands, env vars or operations updates the relevant docs — **this file and `CLAUDE.md` both**.
- **GCP worktree scope stays local and narrow.** `tools/gcp_scope.ts install` owns each mapped repo's generated `.envrc` block and the exact `.envrc` row in `.worktreeinclude`; `check` validates both. Preserve other include rows/comments and never add credentials or broad globs. Codex-managed worktrees consume the file; plain Git-worktree helpers must copy the explicitly named safe files themselves.
  - **A built-in Claude worktree needs the copied `.envrc` trusted (STARK-5090).** `claude -w` copies `.worktreeinclude` entries but never `direnv allow`s the copy, and direnv keys its allow-list by path **and** content hash, so a gcp-scoped worktree opens with `.envrc is blocked`. `config/settings.json`'s third `SessionStart` hook grants it, resolving the worktree **root** from the session cwd (a subdirectory session still trusts the root `.envrc`) and only when that root is a real linked git worktree (`.git` is a file) — a directory merely named `.claude/worktrees/<x>` is never auto-trusted. `matcher: startup` keeps it off `resume`/`clear`/`compact`, so an `.envrc` edited mid-session still needs a human `direnv allow`. It arrives via `setup.sh`, but only since STARK-5223: the template used to merge *under* the live `~/.claude/settings.json` with a shallow `jq '.[0] + .[1]'`, so a live file that already had `hooks` never gained a template hook. setup.sh now unions hook entries per event.

**Pipeline (in order)**

| `/gru start <epic \| --tickets ...>` | **Gru** drives an epic or ticket list to done, one `/minion` per ticket, over alfred + Hermod. No tooling, no store; rerun `start` to resume. Neither Gru nor the Minion writes a ticket custom field (alfred spec STARK-6093): `worker`/`branch` are alfred's at bind, and `pr_url`/`pr_state`/`review_state` belong to whichever path opens or merges the PR — `idun gh pr-open`/`pr-merge`, and in this repo `copilot_land.ts land` and `$stark-author` Phase 6. No `review_evidence_lib.ts` lives here: STARK-6091 deleted its only intended caller (gru's `verifyCompletion`/`settle`) after the spec pinned its base, so idun's copy is the live one, next to the merger that reads it. Each ticket's repo resolves at launch through `frigg repos get` (the call `hermod ticket --repo` itself makes; exit 3 = unregistered); an unresolvable name falls back to a path derived from a registered record's `path`, and that path must be **proved** with `git -C … rev-parse --show-toplevel` first — hermod silently cuts a bad `--cwd`'s worktree from the caller's own repo and exits 0, so an unproved guess works the ticket in the wrong codebase. Unprovable = the ticket is blocked. Seeding the registry is the operator's. Codex uses `$gru`. `start … --new-tab [--repo <name>]` (STARK-7540) makes the session a launcher: `hermod ticket STARK-<epic> --gru` (STARK-7537, after v0.19.0) for a bare epic, a one-line `--prompt-file` brief for every other form, on the epic's id or — under `--tickets` — `GRU-<first ticket's number>`, never a ticket Gru will work (it would read its own peer row as that ticket's Minion and never launch it); checks the launch id's worktree is free first, prints the ack and stops. `--new-tab` starts a Gru, never resumes one. |
| `/minion` | Runs the shared [worker spine](standards/worker-spine.md) + [stand-down contract](standards/stand-down.md) (with `/agnes`). Own one ticket through the repo spine, fix in-scope gaps in the same PR, file a follow-up for a whole effort, verify live (re-run after `--fix`, output posted as a PR comment since stand-down destroys the scrollback) and name that verification in the report, report `done`/`blocked`/`follow-up` to Gru over Hermod, then stand down on `done` with `hermod poison-pill --json` (no behavior-changing flags — after the merge, the ticket close, a clean tree and the report; it targets the session's recorded cwd, not your shell's, so check that tree, and check unpushed work against `origin/<own branch>`, never `origin/main`, which a squash-merge leaves non-empty forever). The pre-arm pane count is two steps — `hermod whoami --json`, then `hermod panes` under the **literal** `workspaceId` it printed — because `$CMUX_WORKSPACE_ID` goes stale when a tab is moved and a bare `hermod panes` then prints nothing over a real count (STARK-7263); a pasted-id slip is retried once, never a reason to skip the stand-down. A `blocked`/stopping exit does not stand down, and neither does a subagent (it shares `$CMUX_SURFACE_ID` and would kill the parent's tab). Standing down needs no go-ahead, and a hand-invoked Minion stands down exactly like a Gru-launched one (with no leader peer, the `done` line is said in-session; the durable evidence is the PR comment either way) — the scope above is what stays non-negotiable; `armed:true` is the only proof it armed and prints only under `--json` — never fire twice. One piece stays in this repo and must not be mistaken for dead code: `config/statusline-command.sh` is the **only** writer of `~/.claude/.cc-usage-<account>_<org>`, since the 5h/7d percentages arrive only in the statusline stdin payload — `idun cc limits` / `next --best` have no other source of headroom for an inactive seat. Cross-language wire contract with `idun/src/cc/cc_lib.ts`; see the comment block above the writer, and `CLAUDE.md`. The 5H/7D **render** is a usage bar per window (STARK-2807), filled by the idun daemon's live poll of the current seat and falling back to the payload reading when the daemon has no fresh entry. The payload windows are frozen to the launch seat, so after a mid-session rotation they belong to the rotated-away seat; rather than gate them (the retired `resolve_startseat`/`usage_windows_stale`/`.statusline-procseat-<sid>` machinery — STARK-2652, now deleted), the render reads the idun daemon's live poll of the current seat from `~/.claude/.idun-daemon-state.json` (same `accountUuid:organizationUuid` seat key) and uses it as each bar's value, falling back to the frozen payload only when the daemon has no fresh entry — the live number without a restart. The daemon read is fork-free; its `== *"<seat>": {*` presence guard is load-bearing (a missing seat would leak a different seat's percentages, and one account can hold seats in two orgs). The bar renders dim-empty with `—` only when neither source has a value (a daemon value < 0 is treated as absent). Separate from the snapshot-write's `.statusline-seat-current` marker guard. STARK-2206 once had the writer block also fire `idun daemon send --from-file` to feed the `idun daemon` quota watcher; **STARK-2807 removed that push** (idun >= 0.26.0 dropped the socket + `send` verb — the daemon now polls the usage endpoint itself for the active seat's real figures). The snapshot WRITE stays (it is still the daemon's boot seed and `idun cc limits`' only source); do not re-add a `daemon send`.

## Distribution

PR landing retains `--lead` as a compatibility argument, echoed in dry-run output only when supplied, and requires `--body` like every other documented-required flag. Authentication patterns return `skipped` with `operator_action_required` in auto mode, before guard commands, verification, budgets, or circuit accounting; in suggest mode they return `suggested` like any other pattern, so canary promotion history is real — while `healer_canary` refuses to promote that action, since auto mode would only ever refuse it. Both runtimes carry the same gate. Read-only GraphQL operations may retry once; uncertain mutations never retry.

## Conventions

- **Docs live with the code** under `docs/`, folder per type — `adr/` (`NNNN-<topic>.md`, immutable: supersede, don't edit), `specs/` (`YYYY-MM-DD-<topic>-spec.md`), `retros/` (`YYYY-MM-DD-<topic>-retro.md`). **That is what `/stark-init-docs` scaffolds into a target repo, guarded by `tools/doc_convention.test.ts` — it is not a layout this repo keeps.** stark-skills carries no `docs/` tree; each skill is documented by its own `SKILL.md` and its `--help`.
- **There is never a `docs/plans/`.** Since `/stark-author` (2026-08-01) the spec carries the plan — task DAG, done-whens, closing verification command.
- Tier by blast radius: trivial → PR only · feature → spec · architectural → ADR + spec.
- Config is JSON, prompts are markdown. **The per-agent × per-domain review prompt corpus is gone** — it belonged to `/stark-review` and was buried with it (STARK-6098). `global/prompts/` now holds one rubric dir per dispatcher (`iac-review/`, `refactor-planner/`), shared by every agent that runs it.
